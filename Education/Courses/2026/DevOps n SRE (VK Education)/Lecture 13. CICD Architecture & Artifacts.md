### CI/CD
Это автоматизация процессов для разработчиков продукта
- CI -- Continuous Integration;
- CD -- Continuous Delivery (or Deployment)


### CI -- это надстройка над git flow
- Регулярная интеграция изменений кода от нескольких разработчиков в общий репозиторий;
- Максимально частая проверка;
- Корректное и быстрое сведение разных изменений вместе.


### CD -- это доп. этапы для ускорения релизов
- Изменения всегда готовы быть опубликованы для пользователей;
- Автоматизация развёртывания в продакшен среду.


### Процесс CI/CD
1. Код в репо;
2. Непрерывная интеграция (CI);
3. Артефакты -- результаты сборки и тестирования;
4. Непрерывная доставка результатов (этапы CD);
5. Развёртывание в продакшен среду;
6. Мониторинг, сбор аналитики, доработки.


### Артефакты
Успешно собранные и протестированные артефакты сохраняются в репозитории артефактов для дальнейшего использования.
Например, GitLab s3, GitLab Package/Container Registry, Nexus, JFrog или Docker Registry.
Артефакты могут представлять собой библиотеки, бинарные файлы, исполняемые файлы или любые другие результаты исполнения джоб, полученные на этапах сборки и тестирования. Например, отчёты.
Артефакты одних джоб используются в других, последующих джобах.

Собираем один раз, версионируем и продвигаем один и тот же артефакт по окружениям (dev/stage/prod), а не пересобираем заново на каждом шаге.

### IaC и DSL
**IaC (Infrastructure as Code)** — описание инфраструктуры в виде кода, а не ручных настроек в UI:
- воспроизводимость;
- версионируемость;
- проверяемость.
    
**DSL (Domain-Specific Language)** — способ писать пайплайны как разработчики пишут код:
- разделение окружений;
- управление секретами;
- контроль изменений;
- стандартизация под единые шаблоны, то есть легкий вход для нового инженера.

### Оптимизации в CI/CD: Build Cache
Повторное использование результатов предыдущих сборок, чтобы не собирать/не скачивать одно и то же каждый раз.

Ускоряет сборку, то есть ускоряет feedback loop для разработчиков.


### Пайплайн состоит из 4 основных фаз
- Предполётная подготовка / Pre-flight Setup / Инициализация инфраструктуры;
- Полёт / Mission Control Operations / Непрерывная интеграция;
- Автопилот / Autopilot / Continuous Delivery;
- Выход на Орбиту / Application Orbit / Continuous Deployment, Monitoring.

### Обучение это билд?

| БИЛД                                 | ОБУЧЕНИЕ                                                  |
| ------------------------------------ | --------------------------------------------------------- |
| Возвращает "бинарный" артефакт       | Возвращает "бинарный" артефакт                            |
| Принимает на вход код и зависимости  | Принимает на вход код, зависимости, данные и параметры    |
| Занимает минуты                      | Занимает часы                                             |
| Делать build через CI — это стандарт | Обучать руками и класть куда-то артефакт — это "стандарт" |
|                                      | DS любят поиграть с параметрами                           |


### Обучение и переобучение
ML модель = КОД + ПАРАМЕТРЫ + ДАННЫЕ + ЗАВИСИМОСТИ + ОКРУЖЕНИЕ

Чтобы изготовить ML модель со свойствами идентичными оригинальной -- нужно взять тот же самый код, те же параметры, те же данные, те же зависимости и то же окружение

![[Pasted image 20260512230530.png]]


## Git LFS (Large File System) vs DVC

| Git LFS                                                                                | DVC                                                            |
| -------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Хранит данные на специальных серваках (рядом с GIT) (есть ограничения на размер файла) | Хранит данные в **HDFS, S3, GOOGLE CLOUD, etc**                |
| Нет связки между кодом, параметрами и данными                                          | Версионируемо хранит связку между кодом, параметрами и данными |
| Не всякий git server поддерживает LFS                                                  | Можно использовать с любым git server                          |

### Подведём итоги
- понимаем как работает конвейер развёртывания;
- делаем путь **commit → проверка → артефакт → деплой** быстрым, повторяемым, наблюдаемым;
- архитектура CI/CD состоит из правил и раннеров, и её качество определяется изоляцией, скоростью, управлением секретами и надежностью исполнения;
- должна быть полная прозрачность: понятно кто породил какой артефакт на каком этапе, чтобы знать как быстро откатиться;
- можно делегировать исполнителя, но нельзя делегировать ответственность.
