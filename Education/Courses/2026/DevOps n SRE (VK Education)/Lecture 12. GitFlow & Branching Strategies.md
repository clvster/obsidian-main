# Git как модель
### Проблемы
- "Вчера ночью всё работало, а сегодня уже нет";
- "Сегодня всё работает, но я не помню, что я сделал";
- "В коде что-то изменилось, но я не помню, что именно".


### Системы контроля версий
Это софт, позволяющий удобно хранить версии файлов. Каждая версия создается **пользователем** (**не автоматически**). Каждую версию нужно снабдить комментарием. Это как «архивы с датами», но удобно и с плюшками.
Файлы могут быть любыми, но большинство СКВ предназначено для текстовых файлов (потому что их легко сравнивать).

**Какую систему контроля версий выбрать?** Это сильно зависит от ваших задач и программного окружения.


### На самом деле, git решает еще многие проблемы:
- удобные резервные копии кода;
- работа в команде;
- работа с разных устройств;
- песочницы для экспериментов;
- «что именно было в релизе»;
- и множество проблем, которых не должно было быть в принципе:
    - поиск причин поломок;
    - откат изменений точечно.


### Версии в git
- каждая версия называется коммит (commit);
- каждый коммит нужно создавать вручную, «само» ничего не произойдет;
- перед этим нужно рассказать git’у немножко о себе — имя пользователя и почту. Это можно сделать один раз, после установки git’а (на всю систему), но можно и индивидуально для каждого репозитория;
- каждый коммит необходимо снабдить комментарием. **Комментарий должен отражать смысл изменений так, чтобы вы понимали их!**;
- для каждого коммита нужно выбрать, какие изменения вы хотите закоммитить;

### Какие файлы не нужно версионировать в git?
Вот расшифровка текста с четвёртого изображения:
- все файлы, которые можно сгенерировать из других:
    - например, листинги компилятора и бинарные файлы;
- временные файлы IDE;
- файлы, которые к проекту не относятся;
- секреты.


### Как поделиться кодом?
git – это распределённая система контроля версий. Это всего лишь значит, что вы можете использовать удаленные репозитории (**remotes**).
Remote может быть просто другой папкой у вас на компьютере или полноценным сервером.


### Как пользоваться ремоутом?
- **`git remote add <url> <name>`**
    - традиционно, если remote только один, его называют «origin»;
- **чтобы отправить код на remote, вы делаете `git push <name>`**
    - разумеется, при этом на remote отправятся только уже сделанные коммиты;
- **чтобы взять код с remote, вы делаете `git fetch`**;

Т.е. если вы пишете код на нескольких компьютерах, вы не таскаете его на флешке и не кладёте в облако, а просто делаете `git push`.



# Branching Strategies
### Ветки
**Проблема:**
- вы хотите попробовать два варианта, но ещё не знаете, какой лучше.
- вы работаете над одним и тем же проектом вдвоём.

**Решение: ветки** (это как альтернативные истории).
Каждая последовательность связанных коммитов называется веткой (branch). Каждая ветка должна иметь имя; ветки без имен удаляются сборщиком мусора. Имя ветки приклеено к последнему коммиту в ней.
Традиционно, «главная» ветка называется главной (main) или мастер (master).
При необходимости можно производить слияние веток (merge) и другие более сложные операции.


### Branching strategy
- как быстро новая правка попадает в main?
- качество? Нужно тестирование.
- предсказуемость релизов — что именно идёт в продакшен среду?
- поддержка = хотфиксы.

### Feature flags
Способ отделить "деплой" от "релиза фичи": код в main, но функциональность выключена:
- эксперименты;
- быстрый откат.


### GitHub / GitLab flow
- develop ветка + Pull / Merge Requests;
- develop всегда готов к деплою;
- Continuous integration;
- Continuous deployment.


### Политика репозитория
- Protected branches: main, develop, release;
- Проверки CI: lint, build, test;
- Codeowners: код ревью.
- Правила именования веток и коммит месседжей: таск трекеры;
- Теги на бета версии, релизы => changelog: автоматизированные списки изменений;
- Роли в репозитории для участников команды проекта в GitLab / GitHub: привилегии.


### Репозиторий на GitLab / GitHub
- подготовка репозитория;
- ветки и выбор политик;
- базовый пайплайн;
- артефакты и отчёты;
- автоматизированный changelog;
- оценка качества выбранной стратегии;
- оптимизации;
- получение репозитория, готового к разработке проекта;


### Подведём итоги 
- git — это граф коммитов, а ветки — простые указатели;
- branching strategy — это договорённость под ваш релизный процесс;
- gitflow, github/gitlab flow — это способ доносить изменения в основную ветку разработки;
- feature flags позволяют держать main ветку всегда готовой к релизу;
- релизы, контроль качества, все правила должны быть закреплены в репозитории технически.
