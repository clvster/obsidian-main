# Application Security (AppSec)
Комплекс мер, принимаемый для обеспечения безопасности разрабатываемого приложения.


### Свойства безопасной системы
- **Конфиденциальность / Confidentiality** — должны быть определены права доступа к разным типам данных.
**Пример:**
данные: никнейм пользователя;
данные: сколько средств на счету;
данные: аватар пользователя.


- **Целостность / Integrity** — система не имеет возможности нарушать атомарность операций.
**Пример:**
Чтобы сумма вычиталась из одного счёта и добавилась к другому, не терялась


- **Доступность / Availability** — онлайн-сервисы всегда доступны.
Система должна соблюдать установленные пороговые требования по доступности.
Любые уязвимости, которые могут привести к отказу системы — нарушают свойство доступности.


- **Апеллируемость / Non-repudiation** — возможность для каждого совершённого в системе действия однозначно определить кто его инициировал.
**Пример:**
У каждого запроса должен быть отправитель.
Нарушение: подменить инициатора.


### Ключевые понятия
- **Актив / Asset** — что охраняем;
- **Уязвимость / Vulnerability** — сломанный замок;
- **Атака / Attack** — действие;
- **Угроза / Threat** — кто может атаку организовать;


### Угрозы -- STRIDE -- техника моделирования угроз
- **Spoofing / подделка** (сумма перевода);
- **Tampering** / вмешательство в систему;
- **Repudiation** / прикинуться кем-то другим;
- **Information disclosure** / нарушение конфиденциальности;
- **Denial of service** / вызов отказа системы;
- **Elevation of privilege** / нарушение правил ролей в системе.


### Контрмеры
- **Security by design**.

# Метрики безопасности
### Как мерить безопасность
- Аудиты и Комплаенс;
- Успешные атаки;
- % регулярно сканируемых систем;
- Количество известных уязвимостей.


### Автоматизация тестирования безопасности
1. **Training (Обучение)**
    - Core training (Базовое обучение)
2. **Requirements (Требования)**
    - Define quality gates/bug bar (Определение порогов качества и планки багов)
    - Analyze security and privacy risk (Анализ рисков безопасности и конфиденциальности)
3. **Design (Проектирование)**
    - Attack surface analysis (Анализ поверхности атаки)
    - Threat Modeling (Моделирование угроз)
4. **Implementation (Реализация)**
    - Specify tools (Определение инструментов)
    - Enforce banned functions (Запрет небезопасных функций)
    - Static analysis (Статический анализ)
5. **Verification (Проверка)**
    - Dynamic/Fuzz testing (Динамическое/Фаззинг-тестирование)
    - Verify threat models/attack surface (Проверка моделей угроз и поверхности атаки)
6. **Release (Релиз)**
    - Response plan (План реагирования)
    - Final security review (Финальный обзор безопасности)
    - Release archive (Архив релиза)
7. **Response (Реагирование)**
    - Response execution (Выполнение мер реагирования)

### DAST (Dynamic Application Security Testing) -- динамическое тестирование безопасности
- можно без доступа к исходникам;
- обнаруживает не потенциальные, а реальные угрозы;
- выявляет проблемы конфигураций и интеграций.

![[Pasted image 20260516105318.png]]


### DAST методологии
![[Pasted image 20260516105352.png|605]]
![[Pasted image 20260516105534.png]]
**Пассивное** сканирование анализирует ответы приложений без отправки потенциально вредоносных запросов:
- Проверяет заголовки HTTP, cookie и содержимое ответов на наличие ошибок в настройках безопасности;
- Выявляет уязвимости, приводящие к раскрытию информации, такие как раскрытые версии сервера или трассировки стека;
- Обнаруживает отсутствующие заголовки безопасности (CSP, HSTS, X-Frame-options);
- Анализирует конфигурацию SSL/TLS и проблемы с сертификатами.

**Активное** сканирование отправляет специально сформированные запросы, предназначенные для активации уязвимостей:
- Проверяет наличие уязвимостей внедрения (SQL-инъекции, XSS, внедрение команд);
- Пытается использовать уязвимости аутентификации и авторизации;
- Проверяет очистку входных данных и кодирование выходных данных;
- Проверяет наличие уязвимостей бизнес-логики.


### Как они дополняют друг друга
- SAST: что потенциально опасно в нашем коде;
- DAST: что реально уязвимо в работающем приложении;
- SCA: что опасно в наших зависимостях и образах.

IAST (Interactive AST): агент в рантайме + тесты -> точнее, чем SAST/DAST по отдельности.
Secrets scanning: поиск ключей/токенов.
Container/IaC scanning: манифесты, Dockerfile, политики.

### Безопасность самого CI/CD
**Секреты и утечки данных в CI/CD (логи, артефакты, переменные).**
Риск: секреты попадают в логи:
- echo $POSTGRES__PROD_DSN, stacktrace, verbose/debug
- "утекают" через: job output, артефакты, кэш, test reports, docker build args, env dump

Ошибки: хранение секретов в .env, репозитории, MR/PR, в переменных без masking.

Контрмеры:
- Masking/Redaction секретов + запрет set -x/debug на prod-джобах;
- Короткоживущие токены вместо статических паролей;
- Сканирование репы/логов на секреты (secret scanning) + exit 1 на найденных секретах;
- Минимизация доступа: разные секреты для dev/stage/prod, принцип least privilege.


**Раннеры и окружение выполнения: привилегии, изоляция, supply chain**
- Риск: privileged runner / Docker-in-Docker → выйти на host, взять токены, подменить сборку;
- Риск: общий (shared) раннер между проектами → пересечение доверенных границ;
- Риск: небезопасные образы для job (tooling image) → встроенный бэкдор в CI. 

Контрмеры:
- Запрет/минимизация privileged, root, hostPath, --network=host;
- Чистка workspace, запрет reuse кэша между проектами;
- Изоляция: отдельные раннеры/пулы для prod, отдельные сети/VPC, egress allowlist;
- Подписанные/проверенные job images, pin по digest, контроль base images;
- Ограничение токенов раннера: минимальные права, ротация, аудит.


**Ошибки конфигурации CI/CD и контроль доступа: кто может деплоить в prod**
- Риск: неправильные права → репортер/внешний контрибьютор может: запустить pipeline с prod-секретами выполнить deploy job или изменить параметры деплоя;
- Риск: небезопасные триггеры: manual jobs без ограничений, pipeline from fork, небезопасные webhooks;
- Риск: -policy bypass-: можно изменить .gitlab-ci.yml/workflow и обойти проверки.
    
Контрмеры (gates и политики):
- Чёткие роли на запуск/изменение pipeline, protected branches/tags;
- Protected environments: деплой в prod только для ограниченной группы + только с аппрува;
- Разделение пайплайнов: build/test для всех, release/deploy — только из main + signed tag;
- -Two-person rule-: аппрувы, обязательные проверки (SAST/SCA/DAST) перед релизом;
- Аудит и мониторинг: прозрачно кто запускал, какие переменные использовал, откуда пришёл pipeline.

# Подписи и сертификаты
### Зачем подписывать артефакт
- Гарантировать подлинность: автор артефакта -- ООО "ВК";
- Обеспечить целостность: артефакт не изменён после сборки -- сравнение по хэш суммам;
- Снизить риск supply chain атак: подмена пакетов, dll, образов, релизов;
- Соответствовать требованиям: маркеты приложений, аудит, регуляторы.


### Что подписываем?
- Артефакты сборки: jar, npm, pypi пакеты, бинарники dll архивы msi, ipa, aab, pkg.
- Контейнерные образы: image signing.
- Манифесты деплоя: Helm charts, Kubernetes YAML, Terraform modules.
- Документы поставки: SBOM, attestation (provenance), release notes.
- Коммиты и теги: Git signing – GPG/SSH.


### Управление инструментами подписи
- Корневой/промежуточный CA, цепочка сертификатов.
- Хранение ключей: Vault, запрет “ключей в репозитории”.
- Ограниченные по времени сертификаты, автоматическое обновление.
- Разделение ролей: build-подпись ≠ release-подпись, least privilege. 
- Отзыв и инциденты: процедуры ротации ключей.


### Как часть CI/CD
Подпись выполняется в доверенной стадии пайплайна Публикация только подписанных артефактов Верификация при деплое: “deny unsigned".


# Policy-as-Code
### Security Quality Gate
![[Pasted image 20260516112214.png]]
1) Выполняется проверка проекта Security анализаторами;
2) Обратно возвращается такой ответ (скриншот);
3) В пайплайне автоматизация проверяет, появилось что-то новое или нет.

Автоматизация может остановить пайплайн в случае нарушение критических политик по безопасности в этой связке "хеш коммита -- проект"


### Отдельно по SCA
**Toxic public repositories:**
Мы ищем, собираем, актуализируем и ведём список toxic public repositories (опенсорсные либы, в которых есть политические лозунги, высказывания, баннеры и тп).

**Корпоративный artifactory:**
Отдаём это все на наши корпоративные nexus артифактори. Если ты у себя где-нибудь в go.mod или requirements.txt занесёшь эту либу, то нексус не отдаст тебе её, и проект не соберется, пайплайн упадет.

**Malware repositories list:**
То же самое делаем для malware пакетов: очень часто npm стреляют. В них вшивают “стилеры” локальных кредов.


### Секреты
Сканирование секретов обычно работает на вебхуках. Если в репозиторий закоммитить и запушишь явный секрет, то в корпоративный мессенджер прилетает уведомление от бота "Ты запушил секрет, проверь".


### Безопасность контейнеров
Частым требованием является проверяться политики, с которыми запускается контейнер: например, чтобы k8s deployment запускался только как _runAsNonRoot_, _readOnlyRootFilesystem_.


### Лицензии
Проверяется лицензионная чистота используемых библиотек. Обычно при настройке правил реализуется не в первую очередь.
