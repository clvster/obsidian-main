### Проблемы CI/CD процессов
Разработчик пушит код -> CI собирает образ -> CD(обычно через kubectl или Helm) применяет изменения в кластер.

**Недостатки**:
1. Кластер можно изменить напрямую (через kubectl edit), что приводит к расхождению состояния;
2. CD-сервер должен иметь широкие права;
3. Сложно увидеть, какая версия где и почему установлена;
4. Бывает трудно откатиться.


### GitOps парадигма
**GitOps предлагает парадигму:** Git — единственный источник истины (single source of truth). Всё состояние кластера описывается декларативно в Git-репозитории. А специальный оператор внутри кластера синхронизирует реальное состояние с тем, что лежит в Git.
Простыми словами GitOps = декларативная инфраструктура + Git + автоматическая синхронизация.
**Разница** между "классическим CD" и GitOps в том, что есть единый источник синхронизации, откуда подтягивается конфигурация на кластер.
**Flux** и **ArgoCD** — два самых популярных инструмента, реализующих GitOps для Kubernetes/Openshift.


### Flux
Flux -- это набор контроллеров в Kubernetes, которые непрерывно следят за Git-репозиторием и применяют изменения к кластеру.
![[Pasted image 20260514123849.png]]


### Основные компоненты Flux v2
- **Source Controller** — извлекает Git-репозитории, Helm-репозитории.
- **Kustomize Controller** — применяет kustomization.yaml.
- **Helm Controller** — управляет Helm-релизами на основе чартов из Git.
- **Notification Controller** — отправляет уведомления (Slack, Teams, GitHub).


### Принцип работы Flux
- Описывается желаемое состояние кластера в Git (YAML-манифесты, Helm-чарты, Kustomize).
- Flux-оператор в кластере сканирует репозиторий (по расписанию или при webhook).
- При обнаружении изменений Flux применяет их в кластер.
- Flux постоянно сверяет состояние — если кто-то вручную правит ресурс, Flux вернёт как в Git (автоматическое исправление дрейфа).

### ArgoCD
**ArgoCD** — декларативный GitOps-инструмент с акцентом на визуализацию и управление сложными развертываниями.

**Ключевые особенности:**
- Есть и Web UI, и CLI с отображением дерева ресурсов (Sync, OutOfSync, Healthy, Degraded).
- **Мультикластерность** — управление сотнями кластеров из одного ArgoCD.
- **SSO & RBAC** — интеграция с OIDC (Keycloak, Dex, GitHub).
- **PreSync/Sync/PostSync хуки** (например, запуск миграций БД до замены подов).
- **ApplicationSet** — генерация десятков приложений по шаблону для разных окружений.


### Архитектура ArgoCD
- **API Server** — gRPC/REST интерфейс, UI.
- **Repository Server** — кеширует Git, Helm, Kustomize.
- **Application Controller** — основной оператор, который держит синхронизацию.
- **Redis (опционально)** — для кеша манифестов.
![[Pasted image 20260514124328.png]]


### Принцип работы ArgoCD
- Пользователь создаёт ресурс Application, указывая Git-репозиторий, путь, целевой кластер/namespace.
- ArgoCD периодически (или при webhook) сравнивает live-состояние с Git.
- Если расхождение — показывает OutOfSync. Можно настроить авто-синхронизацию (как Flux) или ручной режим.
- ArgoCD может «prune» (удалять) ресурсы, которых нет в Git.

### Flux vs ArgoCD: Сравнение
| **Характеристика**                 | **Argo CD**                                                       | **Flux CD**                                                      |
| ---------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------- |
| **Интерфейс**                      | Удобный Web UI + CLI                                              | CLI/контроллер-ориентированный, UI минимален                     |
| **Подход**                         | Приложение-центричный: «Application» CRD                          | Компонентный: GitRepository, Kustomization, HelmRelease и др.    |
| **Мульти-кластер / мульти-тенант** | Поддержка встроена, проекты, RBAC, SSO                            | Поддержка есть, но требует больше инфраструктурной настройки     |
| **Обратные действия / откаты**     | Поддерживаются через UI и CLI                                     | Поддерживаются через Git → revert                                |
| **Простота внедрения**             | Более «готовое» решение, но тяжелее                               | Более лёгкий, минималистичный, гибкий                            |
| **Когда использовать**             | Если нужна наглядность, UI, и команда ориентирована на приложения | Если хотите инфраструктуру как код, меньше UI, больше автоматики |

**Flux лучше подходит для:**
- Монолитных не очень сложных кластеров (1–10 сервисов).
- Команд, которые не хотят поддерживать дополнительный UI — всё через flux CLI и Git.
- Интеграции с Terraform — через tf-controller можно управлять инфраструктурой тем же Git-репозиторием.

**ArgoCD предпочтительнее для:**
- Платформ с сотнями микросервисов — нужен дашборд для SRE/DevOps.
- Крупных организаций с разными командами — SSO + RBAC + логирование действий.
- Мультиоблачных/гибридных сценариев — один ArgoCD управляет кластерами в AWS, On-Prem, GCP.
- Сценариев с канареечными развертываниями — ArgoCD + Argo Rollouts дают blue/green, canary, A/B тесты.
- Регуляторки — нужен аудит, кто и когда синхронизировал кластер с каким коммитом.


### Заключение
- **Flux** — если нужна простота, минимализм, не нужен UI, и ваша команда уже живёт в Git/CLI.
- **ArgoCD** — если нужен дашборд, мультикластерность, строгий RBAC, удобный откат состояний или расширение канареечными деплоями.
- Оба инструмента реализуют **«pull-модель» GitOps** — приложения не пушатся из CI в кластер, а оператор сам тянет изменения из Git. Это сильно повышает воспроизводимость, безопасность и наблюдаемость.
