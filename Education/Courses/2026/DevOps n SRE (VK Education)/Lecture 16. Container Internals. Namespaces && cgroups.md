# Зачем нужна контейнеризация

### У меня работает, у тебя -- нет
Работа приложения зависит не только от кода, но и от окружения, в котором его запускают.

- Разные версии языков, библиотек и системный пакетов;
- Локально всё работает, а на сервере падает;
- Сложность повторить одинаковую среду у всех участников команды;
- Ручная настройка серверов плохо масштабируется.


### Одинаковая среда везде
Контейнер упаковывает приложение вместе с его зависимостями.

- один образ можно запускать локально, в CI, на тесте и в проде;
- меньше сюрпризов между окружениями;
- окружение описано явно, а не настроено руками;
- проще воспроизводить баги и откатываться.


### Проще эксплуатировать
Контейнеры помогают быстрее запускать, изолировать и доставлять приложения.

- Быстрее запуск по сравнению с виртуальными машинами;
- Изоляция процессов, зависимостей и сетевого окружения;
- удобная доставка через образы и registry;
- проще масштабировать и обновлять сервисы;
- база для Kubernetes и современных SRE/DevOps-практик.


Главная идея контейнеризации **уменьшить зависимость приложения от конкретной машины и среды.**
Мы не настраиваем окружение вручную каждый раз, а описываем его. После этого один и тот же артефакт можно запускать в разных средах более предсказуемо.
**Контейнеры не решают все проблемы эксплуатации, но дают удобную базу для воспроизводимого запуска приложений**




# Что такое контейнер

### Что такое контейнер 
Изолированный процесс или группа процессов на хостовой ОС.
- контейнер не содержит отдельное ядро ОС;
- процессы внутри контейнера используют ядро хоста;
- изоляция создаётся средствами Linux;
- Docker удобный инструмент поверх этих механизмов.

### Контейнер ≠ виртуальная машина
Виртуальная машина:
app → libs → guest OS → hypervisor → host OS → hardware

Контейнер:
app → libs → container runtime → host OS kernel → hardware

- ВМ запускает отдельную ОС со своим ядром;
- контейнер использует ядро хоста;
- контейнер обычно стартует быстрее;
- контейнер легче по ресурсам;
- изоляция у ВМ сильнее.


### Образ vs контейнер
Образ (image) — шаблон, из которого запускают контейнер.

Контейнер (container) — запущенный экземпляр образа.

- образ — неизменяемый артефакт;
- контейнер — запущенное (runtime) состояние;
- из одного образа можно назапускать много контейнеров;
- контейнер можно удалить, образ останется;
- изменения внутри контейнера не ведут к изменению образа.


### Путь к запуску контейнер
Dockerfile → docker build → образ → Registry → docker run → запущенный контейнер

- Dockerfile описывает, как собрать образ;
- образ хранит приложение и зависимости;
- registry хранит версии образов;
- контейнер запускается из образа.


### Linux namespaces
Namespaces ограничивают то, что процесс видит вокруг себя, изоляция.

- pid — своё дерево процессов;
- net — свой сетевой стек;
- mnt — свои mount points;
- uts — hostname и domain name;
- ipc — изоляция межпроцессного взаимодействия;
- user — маппинг пользователей внутри и снаружи;
- cgroup — отдельное представление cgroup-иерархии.


### cgroups
- CPU: сколько процессорного времени можно использовать;
- Memory: лимит памяти для контейнера;
- PIDы: ограничение количества процессов;
- IO: контроль доступа к диску;
- accounting: сколько ресурсов потребляет контейнер;
- для docker stats, лимитов и Kubernetes requests/limits.


### Файловая система контейнера
Образ состоит из слоев, контейнер добавляет слой для записи.

- образ состоит из слоев доступных только для чтения (read-only);
- контейнер получает верхний слой для записи (writable layer);
- изменения в контейнере живут в этом слое;
- при удалении контейнера слой для записи исчезает;
- для данных используют тома (volumes) или монтирование (bind mounts).


### Процесс взаимодействия
docker CLI → Docker daemon → containerd → runc → Linux kernel: namespaces, cgroups, mounts

- Docker CLI — команда пользователя;
- Docker daemon управляет объектами Docker;
- containerd отвечает за жизненный цикл контейнеров;
- runc создает контейнер на уровне OCI runtime;
- ядро Linux реально обеспечивает изоляцию.


Контейнер — это Linux-процесс с изолированным окружением и ограниченными ресурсами.

- контейнеры используют ядро хоста;
- namespaces создают изоляцию видимости;
- cgroups ограничивают ресурсы;
- image — шаблон, container — запущенный экземпляр;
- Docker упрощает работу с этими механизмами.




# Экосистема вокруг контейнеров

## Экосистема вокруг контейнеров
- Docker не единственный способ работать с контейнерами;
- есть инструменты для пользователя;
- есть runtime-компоненты под капотом;
- есть стандарты формата образов и запуска контейнеров;
- Kubernetes управляет контейнерами на уровне кластера.

- Инструменты: Docker / Podman
- Оркестрация: Kubernetes
- Registry: Docker Hub / GitLab Registry / Harbor
- Runtime: containerd / CRI-O / runc
- Стандарт: OCI


### Docker
Удобный набор инструментов для сборки и запуска контейнеров.

- docker build — собрать шаблон;
- docker pull/push — скачать или отправить image;
- docker run — запустить container;
- Docker Engine работает как client-server приложение;
- Docker часто используют как точку входа в контейнеризацию.


### containerd и runc
- containerd управляет жизненным цикл контейнеров;
- отвечает за образы, snapshot'ы, запуск и supervision;
- runc — низкоуровневый OCI runtime;
- именно runtime в итоге процесс с namespace/cgroups;
- Docker может использовать containerd под капотом.


### Podman
Похож на Docker по CLI, но устроен иначе.

- deamonless-подход;
- можно запускать rootless-контейнеры;
- CLI во многом похож на Docker;
- умеет работать с pods;
- часто используется там, где важна модель безопасности.


### OCI (Open Container Initiative)
Нужен, чтобы разные инструменты понимали контейнеры одинаково.

- OCI Image Spec — как устроен image;
- OCI Runtime Spec — как запускать container;
- OCI Distribution Spec — как распространять images;
- Стандарт позволяет Docker, Podman, containerd и registry быть совместимыми;
- Без стандарта каждый инструмент мог бы делать свой Docker, плохо совместимый с остальными.


### Kubernetes
Docker запускает контейнеры на машине. Kubernetes управляет контейнерами в кластере.

- Запуск контейнеров на многих нодах;
- Декларативное описание состояния;
- rollout/rollback;
- service discovery и балансировка;
- self-healing;
- и МНОГОЕ другое.


Контейнеризация — это не один инструмент, а набор стандартов и компонентов.

- Docker удобен для старта и практики;
- Podman показывает альтернативный подход;
- containerd/runc находятся ближе к runtime-уровню;
- OCI описывает совместимые форматы и правила;
- Kubernetes управляет контейнерами на уровне кластера.




# Docker на практике
Docker помогает превратить приложение в запускаемый артефакт.

- Собрать приложение в образ;
- Запустить его как контейнер;
- Передать конфигурацию;
- Подключить сеть и хранилище;
- Посмотреть логи и состояние.


### Что Docker умеет
build → run → logs → exec → stop → remove

- собирать образы из Dockerfile;
- запускать контейнеры из готовых образов;
- пробрасывать порты;
- передавать переменные окружения;
- подключать тома;
- объединять контейнеры в сети.


### Какие задачи решает
Docker убирает часть ручной настройки окружения.

- Одинаковый запуск приложения в разных средах;
- Быстрое поднятия dev/test окружения;
- Изоляция зависимостей разных проектов;
- Простая доставка приложений на сервер;
- Удобный формат для CI/CD.


### Где Docker используют в эксплуатации
- Разработчик запускает сервисы локально;
- CI собирает образ и прогоняет тесты;
- Образ отправляется в registry;
- staging/prod берут образ из registry;
- Деплой нужной версии.

- CI/CD
- Сборка артефактов
- Локальная разработка;
- Тестовые окружения;
- Доставка приложений.


### Где Docker полезен для SRE/DevOps
Docker важен как способ стандартизировать запуск сервиса.

- Проще воспроизвести проблему локально;
- Логи можно читать единым способом;
- Сервис можно быстро перезапустить или пересоздать;
- Можно задавать лимиты CPU/RAM;
- healthcheck помогает понять состояние контейнера;
- Docker — база для понимания Kubernetes.


Docker — это популярный, но не единственный инструмент для сборки, запуска и доставки контейнеризованных приложений.

- Docker описывает окружения приложения;
- image становится артефактом поставки;
- container — запущенный экземпляр этого артефакта;
- DevOps использует Docker для CI/CD;
- SRE использует Docker для воспроизводимого запуска и эксплуатации сервисов.


### Без этих команд в Docker никуда
- docker pull — скачать образ;
- docker run — запустить контейнера;
- docker ps — посмотреть запущенные контейнеры;
- docker logs — посмотреть вывод приложения;
- docker stop — остановить контейнер;
- docker rm — удалить контейнер.


### Полезные команды для диагностики
- docker images — какие образы есть локально;
- docker exe -it `<container>` sh — выполнить команду внутри контейнера;
- docker logs `<container>` — посмотреть stdout/stderr контейнера;
- docker ps -a — увидеть всё, в том числе остановленные контейнеры.


Базовые команды Docker закрывают основной цикл работы с контейнером: скачать образ, запустить контейнер, проверить его состояние, посмотреть логи, остановить и удалить.

- Docker помогает пройти путь: код → образ → контейнер;
