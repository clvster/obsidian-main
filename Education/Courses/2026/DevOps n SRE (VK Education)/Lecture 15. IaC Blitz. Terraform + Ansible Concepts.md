# Зачем нужен IaC
### 2009: жизнь до автоматизации
Нужно поднять веб-приложение:
- Заказали сервер у хостера;
- Зашли по SSH;
- apt install nginx php mysql;
- Поправили конфиги;
- Запустили.
Документация? Confluence -- уже устарел.


### ClickOps и его проблемы
1. Невоспроизводимо: тот же сервер второй раз -- слегка другой.
2. Нет истории изменений.
3. Документация устаревает в день написания.
4. Знания -- в голове одного человека (bus factor).
5. Восстановление после сбоя -- долго и неточно.


### Shell-скрипты -- следующий шаг
setup.sh c apt install, cp configs/, systemctl start.

Помогают, но:
- Не идемпотентны: второй запуск сломается;
- Описывают шаги, а не желаемое состояние;
- Упали посередине -- системы в неконсистентном состоянии;
- Кто-то поправил руками -- скрипт не знает.


### Snowflake-серверы
Каждый север уникален как снежинка.

На №1 nginx скомпилирован из исходников;
На №2 -- поставлен из репозитория;
На №3 кто-то правил sysctl.conf под нагрузку;
На №4 забыли применить патч безопасности.

Антипаттерн. Воспроизвести точно -- невозможно.


### Pets vs Cattle
**Pets:** (питомцы)
- У каждого есть имя;
- Лечат, выхаживают;
- Боятся убить;
- Знания о них -- в голове.

**Cattle:** (скот)
- Помечены номерами;
- Заменяют, не лечат;
- Перезапускают без раздумий;
- Знание в коде.


### Configuration drift
Дрейф конфигурации -- со временем "одинаковые" сервера расходятся.

Откуда:
- Кто-то зашёл "потушить пожар";
- Автообновления в разные дни;
- Деплой упал на одном -- никто не заметил;
- Внешние зависимости обновились.
Накапливаются невидимо. Однажды один сервер начинает вести себя странно.


### Идемпотентность
Операция идемпотента, если её результат не зависит от того, сколько раз её выполнять.

Идемпотентно:
- Включить свет;
- Создать файл, если его нет.

Не идемпотентно:
- Переключить свет (toggle);
- Добавить строку в файл.


### Зачем идемпотентность в инфраструктуре
Если применять описание дважды -> результат тот же.

Это даёт: 
- Безопасный повторный запуск;
- Возможность "довести до состояния" после сбоя;
- Смелость менять — потому что откатиться легко.
Без идемпотентности нет IaC.


### Что даёт IaC
1. Воспроизводимость -- из git восстанавливается всё;
2. История -- git log показывает кто, когда и зачем;
3. Код-ревью -- изменения через pull request;
4. Тестирование -- можно поднять идентичный стенд;
5. Самодокументируемость -- код и есть документация.


### Два класса инструментов
**Provisioning:**
- Создаёт ресурсы с нуля;
- Виртуалки, сети, БД, балансировщики;
- Terraform, Pulumi, CloudFormation.

**Configuration Management:**
- Настраивает существующее;
- Пакеты, конфиги, сервисы, юзеры;
- Ansible, Chef, Puppet, Salt.



# Terraform -- декларативный provisioning
### Декларативный vs Императивный
Императивный ("как"):
- Зайди -> проверь -> если нет -> поставь -> скопируй -> запусти.

Декларативный ("что"):
- Хочу: 3 виртуалки + балансировщик + postgresql.


### Terraform = ядро + провайдеры
Ядро не знает ничего про конкретные облака.

Провайдер -- плагин, который умеет говорить с API:
- hashicorp/aws;
- yandex-cloud/yandex;
- integrations/github;
- kreuzwerker/docker;
- cyrilgdn/postgresql.
Один язык для всего, что есть в реестре.


### Три кита Terraform
1. Provider -- как общаться с системой;
2. Resource -- что создать;
3. State -- что уже создано.

State -- самое важное. И главный источник граблей.


### HCL: язык Terraform
```HCL
resource "docker_container" "web" {
    name = "my-web"
    image = "nginx:1.25"
    ports {
        interal = 80
        external = 8080
    } 
}
``` 


### State: слепок реальности
Terraform запоминает: "resource X из конфига = ресурс Y в реальности".

```HCL
{
    "resource": [{
        "type": "docker_container",
        "name": "web",
        "instances": [{"attributes": {"id": "a3f8b..."}}]
    }]
}
```


### State: критичный артефакт
Не коммитить в git -- там бывают секреты.
Один state = одна инфраструктура.
Потерял state -> потерял связь с реальностью.

В продакшене: remote state(S3, Terraform Cloud) + блокировка.


### Lifecycle: 4 команды
```
terraform init # скачать провайдеры
terraform plan # показать разницу
terraform apply # применить
terraform destroy # снести
```

Workflow: edit -> review -> apply.


### terraform plan -- диф между мирами
Terraform читает:
- State -- что было;
- Реальность через провайдеров -- что есть;
- Конфиг -- что должно быть.

И печатает разницу: "+ создать", "- изменить", "- удалить".
Всегда читайте plan перед apply. Это "git diff" инфраструктуры.


### In-place vs Replacement
При изменение ресурса возможны:
- ~ update in-place -- изменение без пересоздания;
- -/+ destroy then create replacement -- удалить и создать заново.

-/+ destroy_container.web (forces replacement).
Опасно для ресурсов с данными (БД, диски).


### HCL: переменные, output, ссылки
```HCL
variable "image_tag" { default = "1.25" }

resource "docker_image" "nginx" { name = "nginx:${var.image_tag}" }

resource "docker_container" "web" { 
    image = docker_image.nginx.image_id # зависимость 
} 

output "container_id" { value = docker_container.web.id }
```


### Граф зависимостей
Terraform строит граф автоматически ссылкам.

docker_image.nginx → docker_container.web → output

Параллелит всё, что независимо. Порядок создания/удаления — обратный
Не нужно прописывать порядок руками.


### Модули -- переиспользование
```HCL
module "web_cluster" { 
    source = "./modules/web-cluster"
    instance_count = 3
    image = "nginx:1.25" 
}
```
Папка с .tf-файлами = модуль; 
Параметры на вход (variable), значения на выход (output);
Публичный реестр: registry.terraform.io


### Итог по Terraform
Декларативный: описываете цель, не шаги;
State: слепок реальности — критичный артефакт;
Workflow: init → plan → apply;
Граф зависимостей строится сам;
Сильная сторона: провижн любых API-ресурсов.



# Ansible -- процедурный configuration management
### Зачем Ansible, если есть Terraform
Terraform создал виртуалку, а что дальше?
- Установить пакеты;
- Положить конфиги;
- Запустить сервисы;
- Добавить пользователей;
- Накатить SSL.
Terraform этого не умеет хорошо. Ему нужно "создать ресурс через API", а не "залезть внутрь машины".


### Архитектура Ansible
1. Inventory -- список машин;
2. Playbook -- что делать;
3. Modules -- единицы работы (apt, copy, service, ...).

Транспорт: SSH;
Агент: не нужен;
Язык: YAML.


### Inventory: список машин
```
[web] 
web1.example.com 
web2.example.com

[db] 
db.example.com

[web:vars] 
ansible_user=deploy
```


### Playbook: YAML-сценарий
```YAML
- name: Setup web servers
  hosts: web
  become: yes
  tasks:
    - name: Install nginx
      apt: { name: nginx, state: present }
    - name: Start nginx
      service: { name: nginx, state: started, enabled: yes }
```


### Modules: единицы работы
apt, yum, pacman — пакеты;
service, systemd — сервисы;
copy, template, file — файлы;
user, group — учётки;
lineinfile, blockinfile — правки конфигов;
сотни cloud-модулей: ec2_instance, digital_ocean_droplet, ...

Большинство штатных модулей идемпотентны.


### Push vs Pull
**Push (Ansible):**
- Центр -- хосты по SSH;
-  Без агента;
- Изменения по команде.

**Pull (Puppet, Chef)**:
- Агент опрашивает центр;
- Нужен агент на каждом;
- Постоянная сходимость.


### Push: цена удобства
**Плюсы:**
- Не нужен агент на машинах;
- Низкий порог входа;
- Хорошо ложится в CI/CD.

**Минусы:**
- Запускается явно — не "вечно держит состояние";
- Дрейф между запусками не виден.

Для compliance ('проверяем каждые 30 мин') часто берут pull-системы.


### Roles: переиспользование
```
roles/nginx/
├── tasks/main.yml
├── handlers/main.yml
├── templates/
├── files/
├── defaults/main.yml
└── meta/main.yml
```
Подключение в playbook:
```YAML
hosts: web 
roles: [nginx, app]
```
Публичная галерея: Ansible Galaxy.


### Variables • Templates • Handlers
Variables — переменные на уровнях: роль, группа, хост, CLI;
Templates — Jinja2 для генерации конфигов;
Handlers — отдельные task'и, запускаются только при notify.

```YAML
- name: Copy nginx config
  template: { src: nginx.conf.j2, dest: /etc/nginx/nginx.conf }
  notify: Restart nginx # запустится только если изменилось
```


### Что Ansible НЕ делает хорошо
Не ведёт state.
Если виртуалку удалили руками — Ansible не узнает.
Не строит граф зависимостей. Выполняется сверху вниз. 
Cloud-модули есть, но это не его сильная сторона.

Создавать инфраструктуру → Terraform. 
Настраивать её → Ansible.


### Итог по Ansible
Процедурный (но из идемпотентных кирпичей);
Push по SSH, без агента YAML + модули + Jinja2-шаблоны;
Не имеет state — каждый запуск опрашивает машину заново;
Сильная сторона: настройка существующих машин.


# Сравнение
**Terraform:**
- Декларативный;
- Хранит state;
- API облака;
- HCL;
- Создание ресурсов.

**Ansible:**
- Процедурный (идемп. модули);
- Опрашивает каждый раз;
- SSH push;
- YAML;
- Настройка машин.


### Когда, что использовать
Terraform — если задача создать/удалить ресурс через API:
- виртуалки, сети, балансировщики, S3, DNS, IAM, репозитории...
    
Ansible — если задача настроить уже существующую машину:
- пакеты, конфиги, юзеры, сервисы, деплой приложения...

Серая зона — DNS, пользователи в БД, k8s-манифесты. Решает команда.


### Стандартный паттерн: Terraform -> Ansible
1. Terraform создаёт виртуалки, сети, балансировщики;
2. На выходе — IP-адреса машин (output);
3. Динамический inventory Ansible подхватывает список машин;
4. Ansible заходит на машины и накатывает конфигурацию.

Разделение ответственности: каждый отвечает за свой слой.


### Альтернатива: Immutable Infrastructure
Packer запекает образ заранее (с приложением внутри);
Terraform разворачивает готовый образ;
Ansible не нужен в рантайме.

Плюсы: быстрый запуск, нет дрейфа, откат = развернуть прошлый образ;
Минусы: не для stateful-систем, дольше итерация при разработке.


# Практики и грабли
Не делайте так: 
```git
git add terraform.tfstate 
git commit -m 'save state'
```

Делайте так: 
``` HCL
terraform { 
    backend "s3" { 
        bucket = "my-tfstate"
        key = "prod/terraform.tfstate"
        dynamodb_table = "tf-locks"
        encrypt = true 
    } 
}
```


### Секреты -- НЕ в код
Куда не класть:
- В Terraform-файлы;
- В Ansible playbook'и;
- В state-файл напрямую;
- В env-переменные CI без шифрования.

Куда класть:
- Vault (HashiCorp);
- AWS Secrets Manager / Yandex Lockbox / GCP Secret Manager;
- SOPS (шифрование YAML/JSON);
- Ansible Vault (для Ansible-переменных).


### Модульность
Terraform: модули. Ansible: роли.

**Правила**:
- Один модуль/роль = одна осмысленная вещь;
- Не "создать пользователя" — слишком мелко;
- Не "развернуть всю инфру" — слишком крупно;
- Параметризуйте, но не переусложняйте;
- Версионируйте.


### GitOps для IaC
Git — источник правды для инфраструктуры.

Никаких "apply с ноута";
Все изменения через pull request;
В PR — terraform plan как комментарий;
Merge в main → CI запускает apply;
main = состояние продакшена.

Цена: дисциплина. Никаких ручных правок в облаке.


### Drift detection
Terraform: plan сам показывает дрейф. 
`terraform plan -detailed-exitcode # exit 2 = есть изменения.`

`Ansible: dry-run` через `--check`. 
`ansible-playbook site.yml --check --diff`

Если кто-то полез руками — система должна заметить и пожаловаться.


### Тестирование IaC
**Terraform:**
- Lint: terraform validate, tflint;
- Format: terraform fmt;
- Integration: Terratest, Kitchen-Terraform.

**Ansible:**
- Lint: ansible-lint;
- Format: ansible-lint --fix;
- Integration: Molecule.


### Топ-граблей: запомнить
1. Никогда не коммитить state;
2. Не редактировать ресурсы руками, если ими управляет Terraform;
3. Всегда смотреть plan перед apply;
4. Думать про destroy — prevent_destroy для критичных;
5. Использовать модули, а не shell в Ansible;
6. Секреты — отдельно, не в коде.


# Итоги
### Что унесли
IaC = воспроизводимость + ревью + история + борьба с дрейфом;
Идемпотентность — без неё инструменты не работают;
Terraform — декларативный provisioning, state — центр вселенной;
Ansible — push CM, идемпотентен на уровне модулей;
В реальной жизни — дополняют друг друга;
Подводные камни — знать, чтобы не наступить.
