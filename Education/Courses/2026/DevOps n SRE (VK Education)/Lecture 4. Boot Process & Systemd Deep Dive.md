### Chain of Trust in Ubuntu
- Прямая подпись ядра ключом Microsoft нерациональна для цикла разработки;
- Решение Canonical: использование промежуточного загрузчика shim (shim-signed);
- shim имеет подпись Microsoft, которую принимает мат. плата;
- Внутри бин. файла shim вшит собственный сертификат Canonical;
- shim проверяет подпись основного загрузчика GRUB2, сохраняя непрерывность доверия.

Secure Boot в UEFI супер-важен! Не снимаем с неё галочку, ибо он будет подвержен к атакам, которые мы никогда не сможем обнаружить.


### Unified Kernel Image (UKI) in Ubuntu


### Рождение PID 1
- Процесс с ИД 1 является прародителем всех остальных процессов;
- В Ubuntu 24.04 файл /sbin/init (systemv в современном мире systemd) является симлинком на /lib/systemd/systemd;
- Ядро переходит в пассивный режим обработки системных вызовов и прерываний;
- Управление сервером полностью делегируется системному менеджеру;
- Начинается фаза асинхронного запуска пользовательских демонов.


### Проблемы устаревшего SysVinit
- Bash-скрипты выполнялись строго последовательно (синхронно);
- Использовалась жёсткая система числовых префиксов (S01, S02) в runlevels;
- Отсутствие встроенного контроля за состоянием демона после запуска;
- Долгие сетевые таймауты в одном скрипте полностью блокировали загрузку остальных;
- Сложность поддержания порядка зависимостей.


### Философия и архитектура systemd
- Отказ от скриптов в пользу декларативного ini-подобного синтаксиса;
- Агрессивная параллелизация задач при старте;
- Построение ациклического ориентированного графа (DAG) зависимостей;
- Использования изоляции ядра (cgroups и namespaces) из коробки;
- Единая стандартизированная плоскость управления сервером.

Грубо упросить жизнь сисадминам, но оно так сильно расширилось, что стало монструазных размеров и возможностей.


### Интеграция шины D-Bus
- D-Bus - система межпроцессного взаимодействия (IPC)
- Позволяет демонам асинхронно сообщать PID 1 о своей готовности (Type=notify)
- Устраняет необходимость в использовании костылей вроде sleep 5 в скриптах запуска
- Является основным API для взаимодействия с systemd из командной строки
- Поддерживает активацию сервисов по сигналу на шине.


# Топология юнитов и графы зависимостей

### Иерархия директорий systemd
- /usr/lib/systemd/system/ - файлы upstream (поставляемые через apt);
- /run/systemd/system/ - эфемерные юниты, генерируемые в реальном времени (это не трогаем); 
- /etc/systemd/system/ - пользовательские настройки администратора (SRE);
- Строгий приоритет: файлы в /etc полностью перекрывают файлы в /usr;
- Изменение файлов в /usr/lib/ вручную категорически запрещено.


### Механизм Drop-in файлов (override.conf)
- Служит для точечного изменения одной директивы (например, лимита памяти);
- Создаётся в директории <имя_юнита>.service.d/
- Утилита systemctl edit <"unit"> (без кавычек) автоматизирует создания этих файлов;
- Сохраняет базовый юнит вендора нетронутым для получения патчей безопасности;
- Применяет поверх основного файла конфигурации на лету.


### Основные типы юнитов (.service и .target)
- .service: Управляет демонами. Определяет ExecStart, Restart, Type;
- Type=simple: Считается запущенным сразу после выполнения команды;
- Type=notify: Ожидает сигнала готовности через D-Bus;
- .target: Логическая точка синхронизации, замена старых runlevels;
- multi-user.target: Эквивалент классического режима.


### Типы юнитов (.socket и .timer)
- .socket: Описывает сетевой или UNIX-сокет. Используется для ленивой загрузки;
- .timer: Замена демона cron с миллисекундной точностью;
- Таймеры предотвращают наложения задач (overlapping), если предыдущая ещё выполняется;
- Таймеры интегрированы в общий журнал логов systemd;
- Поддержка монотонного времени (OnBootSec=) и календарного (OnCalendar=);


### Socket Activation
- Systemd заранее создаёт прослушивающий порт до запуска самого демона;
- При поступлении пакета ядро буферизует его, а systemd запускает сервис;
- Файловый дескриптор сокета (FD) бесшовно передаётся приложению;
- Если сервис простаивает, он может быть выгружен из ОЗУ;
- Архитектура заимствована и улучшена из классического демона inetd.


### Разрешение Race Conditions через сокеты
- Классическая проблема: микросервис A падает, потому что база данных B ещё грузится;
- Решение через сокеты: оба сервиса стартуют абсолютно одновременно;
- Сервис A отправляет запрос к базе B;
- Поскольку сокет базы B уже существует, ядро просто приостанавливает запрос сервиса A;
- Как только база B инициализируется, она мгновенно обрабатывает ожидающий запрос.


### Зависимости доступности (Wants VS Requires)
- Обе директивы указывают системному менеджеру запустить связанные юниты;
- Requires=: Строгая (жёсткая) зависимость. Падение дочернего сервиса убьёт родительский;
- Wants=: Мягкая зависимость. Если дочерний сервис не запустится, родитель продолжит работу;
- В SRE-практиках Wants= является абсолютным стандартном по умолчанию;
- Применение Requires= ограничено критическими компонентами оборудования.


### Зависимости порядка (Before VS After)
- Requires и Wants НЕ управляют порядком старта во времени;
- По умолчанию systemd запускает зависимые юниты параллельно (или пытается);
- After=: Не запускать текущий сервис пока указанные не перейдёт в состояние active;
- Before=: Запустить текущий сервис до старта указанного;
- Комбинация Wants=X и After=X - самый частый паттерн в [UNIT].


### Неявные зависимости (Implicit Dependencies)
- **Менеджер systemd** автоматически добавляет связи, анализируя тип юнита;
- Пример 1: Юниты с `Type=dbus` неявно получают `Requires=dbus.socket`;
- Пример 2: Юниты `.mount` автоматически получают зависимости от файлов устройств (`.device`);
- Снижает размер конфигурационных файлов (принцип DRY);
- Позволяет избежать тривиальных синтаксических ошибок.
