# Основные задачи CDN
**Ускорение загрузки контента:**
- Кэширование статических файлов на серверах, расположенных ближе к пользователям.

**Повышение отказоустойчивости и доступности:**
- Балансировка нагрузки между серверами CDN. Автоматическое переключение на резервные серверы при сбоях.

**Оптимизация трафика и снижение нагрузки на origin:**
- Оффлоад трафика с ориджина, уменьшая его нагрузку.

### Маршрутизируем пользователя в сервер
**Anycast** -- чисто сетевой подход со сложными возможностями **контроля распределения нагрузки**.
![[Pasted image 20260513002123.png]]


**На примере запроса GET example.com/index.html:**
- OS узнает `IP` example.com при помощи DNS-резольвера
![[Pasted image 20260513002444.png]]


### Anycast
**Браузер приходит в веб-сервер example.com и просит index.html:**
- index.html содержит ссылки вида cdn.example.com/<путь до статики>
![[Pasted image 20260513002730.png]]


**OS узнаёт IP cdn.example.com при помощи DNS-резольвера:**
- DNS отвечает anycast адресом группы CDN серверов
![[Pasted image 20260513002844.png]]


Подсеть 192.0.2.0/24 -- это выделенная Anycast подсеть, анонсируя с нескольких (всех) площадок.
Пользователь приходит в ближайшую (с точки зрения BGP) площадку.
![[Pasted image 20260513003143.png]]


Все серверы на площадке имеют одинаковые IP адреса 192.0.2.1.
Построенная сеть позволяет использовать ECMP балансировку до серверов. 
![[Pasted image 20260513003355.png]]
![[Pasted image 20260513003426.png]]

| Плюсы                                               | Минусы                                                                 |
| --------------------------------------------------- | ---------------------------------------------------------------------- |
| Простота внедрения при наличии PI адресов + BGP ASN | Сложно управлять маршрутизацией в случае перегрузки отдельных стыков   |
| Не требуется интеграция с бэкендом приложения       | Сложно управлять нагрузкой и приземлением пользователя в нужный сервер |
| Быстрая реакция на выход из строя площадки целиком  | Могут возникнуть проблемы в случае потери части кэшей на площади       |


### Global Server Load Balancing (GSLB)
GSLB -- технология балансировки нагрузки, которая распределяет трафик между серверами, расположенными в разных географических точках, в основном, основываясь на DNS.
![[Pasted image 20260513004254.png]]


**На примере запроса GET example.com/index.html:**
- OS узнает `IP` example.com при помощи DNS-резольвера
![[Pasted image 20260513002444.png]]
- OS узнаёт IP cdn.example.com при помощи GSBL DNS сервера;
- OS отвечает IP адресом конкретного CDN сервера, в зависимости от IP пользователя и других параметров.
![[Pasted image 20260513004618.png]]
![[Pasted image 20260513004655.png]]
- Разные подсети анонсируют с разных точек присутствия;
- Пользователь придёт в ту площадку, откуда анонсируются подсеть IP адреса, который ему отрезолвил GSLB DNS.
![[Pasted image 20260513005006.png]]
- Все серверы на площадке имеют разные IP адреса в пределах подсети, выделенной на площадке;
- Трафик от пользователя приходит в определённый сервер.
![[Pasted image 20260513005150.png]]

| Плюсы                                                                                | Минусы                                                                      |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| Возможность маршрутизировать пользователя в ближайший сервер с оптимальной загрузкой | Вычисление по IP может быть не точным                                       |
| Возможность частично снимать нагрузку с сервера                                      | Надо "что-то делать", если сервер, IP которым ответили, стал недоступен     |
| Не требуется интеграция с бэкендом приложения                                        | Провайдеры могут не поддерживать ENDS/кэшировать ответы дольше, чем следует |
|                                                                                      | Не учитывается тяжесть/популярность контента                                |


### Application Layer Load Balancing
**Application Layer Load Balancing — интегрируем CDN и backend**:
- Генерируем уникальные ссылки ведущие в конкретный сервер.

**На примере запроса GET example.com/index.html:**
- OS узнает `IP` example.com при помощи DNS-резольвера;
![[Pasted image 20260513002444.png]]
- Браузер приходит в веб сервер **example.com** и просит **index.html**;
- **Index.html** генерируется бэкэндом исходя из локации пользователя, и содержит уникальные ссылки, например, **[cdn1-1.example.com/](https://gemini.google.com/u/1/app/1c30f1023a097e0a?pageId=none)<путь до статики>**;
![[Pasted image 20260513011406.png]]
- **GSLB**: OS узнает IP **cdn1-1.example.com** при помощи DNS сервера;
- **GSLB**: DNS отвечает IP адресом конкретного CDN сервера;
![[Pasted image 20260513011516.png]]
- **GSLB**: Разные подсети анонсируются с разных точек присутствия;
- **GSLB**: Пользователь придет в ту площадку, откуда анонсируется подсеть IP адреса, fqdn которого у него был в index.html;
![[Pasted image 20260513011718.png]]
- Все серверы на площадке имеют разные IP адреса в пределах подсети, выделенной на площадке;
- Трафик от пользователя приходит в определенный сервер.
![[Pasted image 20260513012025.png]]


| Плюсы                                                                                        | Минусы                                                                                   |
| -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Можно максимально точно приземлять пользователя на сервер и кешировать только популярное     | Требуется сложная интеграция с бэкендом чтобы он понимал состояние и архитектуру CDN нод |
| Можно понять какой контент популярный                                                        | Надо «что то делать», если сервер, fqdn/IP которым ответили, стал недоступен             |
| Можно понять рост популярности контента и начать превентивно загружать контент в другие кеши | Проблемы с перемещающимися пользователями                                                |
|                                                                                              | Проблемы с шарингом ссылок                                                               |


# Отслеживание доступности/качество
- Серверные метрики достаточно легко снимать, но они не учитывают то, как пользователь пришел в сервер.
- Хотелось бы и со стороны пользователя понять:
    - Когда появился первый кадр видео;
    - Когда загрузилась картинка;
    - Когда был получен последний байт;
    - Сколько времени заняло получение контента.
- Это важно знать, так как географическая близость к площадке не означает реальную сетевую близость к ней. Если рядом с пользователем несколько площадок, хотелось бы отдать ему лучшую.
